# Решение: объединить только Catalog и Order

В ДЗ №1 Catalog и Order владели разными БД. Пункт 7 ДЗ №2 требует атомарно менять заказ, остатки и промокод. Поэтому объединён только этот контур: **Commerce = Catalog + Order**. User остаётся отдельным сервисом; границы Feed, Payment и Notification из ДЗ №1 не меняются.

```text
Клиент → Gateway :8080 → /auth/* → User       → БД users
                      → остальное → Commerce → БД commerce
                                   обе БД в одном PostgreSQL
```

## Что оставлено для учебного проекта

- Три Go-бинарника: User, Commerce, Gateway. Пакеты users и commerce друг друга не импортируют.
- Один PostgreSQL-контейнер, две БД, два непривилегированных владельца с разными паролями. PUBLIC не имеет CONNECT к этим БД; сервис не может подключиться к чужой БД. Это изоляция данных, но общий домен отказа PostgreSQL — допустимый учебный компромисс.
- User подписывает EdDSA JWT; Commerce проверяет открытым ключом без HTTP-запроса к User. Gateway только пересылает запросы и создаёт request_id, без повторных JWT/OpenAPI-проверок.
- seller_id нового товара берётся из JWT. Назначение другого продавца и вспомогательный GET /users/{id} исключены как необязательные. ADMIN по-прежнему меняет и удаляет любые товары.
- Два Flyway-набора с отдельными историями версий. Инициализация PostgreSQL создаёт только БД/роли, не заменяет Flyway.
- Один E2E-сценарий запуска: настоящие контейнеры Compose. Отдельный скрипт проверяет отказ User.

## Почему транзакция атомарна

Все торговые таблицы принадлежат Commerce и изменяются одной pgx.Tx. UUID пользователя — внешняя ссылка без межбазового FK. Локальная checkout_locks(user_id) сериализует операции одного пользователя, не хранит его профиль.

Порядок блокировок: checkout_locks → заказ → товары по UUID → промокод. Лимит операций и активный заказ проверяются после блокировки; частичный уникальный индекс дополнительно запрещает два активных заказа. Ошибка откатывает все изменения. Saga, 2PC, брокер и сетевой вызов внутри транзакции не нужны.

## Трактовки задания

- Процентная скидка выше 70 даёт нулевую скидку: буквальное прочтение «иначе цена 100%».
- Отмена разрешена из CREATED и PAYMENT_PENDING согласно тексту операции; повторная отмена не возвращает остатки второй раз.
- Повторяющиеся product_id в запросе отклоняются; цена сохраняется снимком в order_items.
- PUT пересчитывает промокод. Если сумма ниже минимума, промокод снимается, использование возвращается.
- User недоступен: register/login/refresh дают 503, Commerce продолжает работу с выданным access до истечения TTL.

Схемы БД и JWT-ключи при упрощении не менялись: аккаунты, парольные хеши, refresh-токены и торговые записи переносятся без изменения. Старые тома сохраняются. Детали конкретной проверки — в [отчёте](verification.md).
